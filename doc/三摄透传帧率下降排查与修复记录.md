# 三摄透传帧率下降排查与修复记录

## 1. 问题背景

单车灯三摄互补功能接入后，核心1需要同时完成以下任务：

- 以100 Hz调度两块2BL3图像板的控制事务。
- 在有新帧时转发latest-only三摄结果。
- 处理下摄图像并通过IPC发布给核心0。
- 在地面调试状态刷新图像调试屏幕。

三摄通信采用异步SPI状态机。`CameraSpi_Update()`只负责启动一轮事务，后续必须由主循环持续调用`CameraSpi_Service()`推进，不能把它当成已经完成的同步调用。

## 2. 故障现象

首次联调时观察到：

| 指标 | 异常值 |
| --- | --- |
| 核心1调度频率 | 约67 Hz |
| 前摄来源帧率 | 约33 FPS |
| 后摄来源帧率 | 约48～49 FPS |
| 前摄SPI事务平均耗时 | 约13～16 ms |
| 后摄SPI事务平均耗时 | 约0.8～2 ms |
| CRC、READY超时、SPI硬件错误 | 0 |

关闭relay透传后，前摄帧率和核心1调度频率仍未恢复。这说明通信数据量会占用总线，但不是本次前后摄严重不对称的直接根因。

## 3. 排查过程

### 3.1 排除2BL3图像算法变慢

在两块2BL3上使用1000帧性能窗口统计图像锁存、车灯搜索和整帧处理时间。结果表明图像算法耗时没有出现足以解释前摄33 FPS的增长，两块图像板本身也仍能持续产生新帧。

### 3.2 排除SPI物理链路故障

检查主从两端的CRC、READY超时、硬件错误、重复帧和乱序帧计数，均未持续增长。前摄事务虽然耗时异常，但最终可以完成，特征更接近软件未及时推进状态机，而不是物理传输失败。

### 3.3 关闭relay验证通信数量

临时关闭两笔latest-only relay，只保留前、后摄两笔控制事务。前摄仍约33 FPS，说明四笔事务不是导致故障的必要条件，应继续检查主循环调度顺序。

### 3.4 根据事务耗时定位调度间隙

前摄事务始终在一轮SPI的最前面启动，却比后摄多出约10～16 ms等待。后摄事务位于下摄图像处理之后，可以连续得到服务。该不对称现象说明：前摄事务启动后，核心1先进入了耗时的下摄整帧任务，直到图像处理完成才再次调用`CameraSpi_Service()`。

### 3.5 对比历史提交确认回归点

对比Air提交`b017a4d`和`36e6307`：

- `b017a4d`在执行下摄图像任务前调用`CameraSpi_Service()`；SPI仍有硬件事务时立即返回主循环。
- `36e6307`删除了这段保护，改为先执行下摄图像处理，再继续推进SPI。

同时，`g_image_tick_100hz`使用饱和标志语义。主循环繁忙时不会累计所有遗漏周期，因此一次10～16 ms阻塞不只延迟当前事务，还会直接降低实际调度频率。

### 3.6 修复调度后发现屏幕阻塞

恢复SPI优先调度后，前后摄帧率恢复对称，但核心1性能统计显示：

- 下摄图像任务最大约4.8 ms。
- IPC轮询和发布为微秒到百微秒量级。
- `ImageDebugScreen_Update()`最大约19.5 ms。

DATA页面每次连续刷新6个240×16像素区域。按20 MHz屏幕SPI计算，纯传输理论耗时已接近18.4 ms，与实测一致。

飞行状态已有“仅待机且未解锁时允许刷新”的保护，因此该问题主要影响地面调试，不影响正常飞行时的屏幕刷新路径。

## 4. 根因

本次问题由两个独立的软件调度问题叠加造成：

1. **核心1异步SPI调度顺序回归。** 前摄事务启动后进入不可抢占的下摄整帧处理，状态机约10～16 ms得不到服务，造成前摄约33 FPS、后摄约48 FPS的不对称。
2. **地面DATA屏幕无条件整块刷新。** 稳定数据仍重复发送6行像素，每次可能阻塞约19.5 ms，进一步降低地面调试时的主循环响应速度。

relay数量、2BL3图像算法、IPC和SPI物理链路均不是此次故障的根因。

## 5. 修复方案

### 5.1 核心1调度修复

核心1主循环固定采用以下顺序：

1. 最高优先级调用`CameraSpi_Service()`。
2. SPI仍有硬件事务时立即返回主循环，不进入下摄整帧处理。
3. SPI轮次结束后执行下摄识别、IPC发布和屏幕更新。
4. 最后消费100 Hz饱和tick并调用`CameraSpi_Update()`启动下一轮。

该修复保持非阻塞状态机，不引入等待循环，也不改变下摄、IPC或控制链接口。

### 5.2 恢复latest-only relay

恢复最繁忙周期两笔control加两笔relay：

- 每个目标板每轮最多发送一笔relay。
- 每个“目的板+来源摄像头”只保存最新帧。
- 无新来源帧时不发送，不积压旧帧。
- 固定128字节SPI事务和现有CRC保持不变。

### 5.3 DATA屏幕局部刷新

DATA页面改为每轮最多检查一行，并且只在有效位、坐标、面积等实际显示值变化时刷新该行。稳定数据不再产生屏幕SPI传输。图像页面仍保留整帧显示，仅用于地面调试。

## 6. 修复结果

完整relay恢复后的两次1000周期实测结果如下：

| 指标 | 实测结果 |
| --- | --- |
| 核心1调度频率 | 100.08 / 100.11 Hz |
| SPI轮次启动/完成 | 1000 / 1000 |
| tick丢失、周期超时 | 0 |
| 最大完整周期 | 6.69 / 7.37 ms |
| 前摄来源帧率 | 约47.75～48.24 FPS |
| 后摄来源帧率 | 约47.95～48.44 FPS |
| 下摄处理帧率 | 约46.1～49.4 FPS |
| SPI平均完整轮次 | 约1.98 ms |
| SPI最大完整轮次 | 约2.75 ms |
| 稳定DATA屏幕耗时 | 约5 us |
| CRC、SPI超时、硬件错误 | 0 |
| 跳帧、乱序 | 0 |

后摄曾出现1～3次非物理控制响应错误，比例低于0.3%，未造成持续掉帧或链路中断。该现象保留为后续观察项，不与本次调度根因混为一类。

## 7. 防回归规则

- 异步SPI事务启动后，必须在主循环最高优先级持续推进，事务完成前不得进入不可抢占的整帧任务。
- 不允许在状态机外增加毫秒级阻塞等待来掩盖调度问题。
- 100 Hz饱和tick不改为积压队列，避免繁忙后突发补跑任务；必须通过保证单周期预算消除丢tick。
- 地面显示必须按变化、分批刷新；稳定页面不得无条件重发整块像素。
- relay必须保持latest-only，不能为旧帧建立排队队列。
- 性能问题应先分离验证算法耗时、总线传输、状态机等待和显示阻塞，不能只根据“增加了通信”推断根因。
- 修改核心1主循环顺序后，至少复核100 Hz调度、三摄帧率、完整轮次耗时、IPC发布和SPI错误计数。
