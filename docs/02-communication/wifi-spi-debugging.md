# WiFi SPI 调试

## 为什么需要 WiFi SPI？

WiFi SPI 不是飞起来所必需的东西，但是在我看来，一套好用的高频遥测链路几乎是从头写飞控所必需的东西。

我们调的不是基于成品飞控二次开发的应用层程序，而是直接在 MCU 上写最底层的传感器、估计和控制。如果没有办法看到无人机运行时的原始传感器数据、估计器中间量和控制器输入输出，那么整个算法就是一个盲盒系统。最后只能看飞机“往哪边歪了”“震得厉不厉害”，再反推可能是哪段代码有问题。我觉得这种调试方式非常低级，而且越到后期越浪费时间。

所以我希望这套调试工具至少满足下面几点：

- 能看高频、尽量原始的数据，最好能跟上 `1 kHz` 的控制节拍。
- 想加什么变量就加什么变量，不用每次重新设计一套协议。
- 尽量不侵入飞控，不应该因为上位机卡了、电脑没开或者 WiFi 模块没插，就把控制环一起拖住。
- CPU 和通信耗时必须能算、能测，不能觉得“肉眼看起来不卡”就当作没有开销。

我后面分析 IMU 的时域和频域、看 `car_plan` 的路径规划、同时回传三个摄像头识别到的信标和车灯坐标、检查姿态和控制器输出，基本都离不开这套 WiFi SPI。

> 这套驱动最重要的原则其实只有一句话：**遥测数据可以丢，但飞控绝对不能等遥测。**

## 代码从哪里看

WiFi 上层协议都放在 [`project/code/Protocols/wifi`](../../project/code/Protocols/wifi/) 下，底层 SPI 驱动在 [`zf_device_wifi_spi.c`](../../libraries/zf_device/zf_device_wifi_spi.c)。如果只是想理解整体结构，可以先看 [`WiFi 协议总览`](../../project/code/Protocols/wifi/README.MD)，再按下面的顺序往下追：

| 模块                                                                      | 主要作用                                                       |
| ------------------------------------------------------------------------- | -------------------------------------------------------------- |
| [`wifi_cmd`](../../project/code/Protocols/wifi/wifi_cmd/)                | 初始化 WiFi、建立 UDP Socket、推进收发、解析文本命令和统一回包 |
| [`wifi_justfloat`](../../project/code/Protocols/wifi/wifi_justfloat/)    | 给数据加时间戳，打包成 VOFA+ JustFloat 格式，再放进软件队列    |
| [`wifi_params`](../../project/code/Protocols/wifi/wifi_params/)          | 按白名单读取、修改、保存和加载飞控参数                         |
| [`wifi_cal_imu`](../../project/code/Protocols/wifi/wifi_cal_imu/)        | 把上位机发来的 IMU 标定命令转给校准程序                        |
| [`wifi_image`](../../project/code/Protocols/wifi/wifi_image/)            | 切换到图像传输模式时发送图像数据                               |
| [`zf_device_wifi_spi.c`](../../libraries/zf_device/zf_device_wifi_spi.c) | 真正和 WiFi 模块通信，里面是我修改后的发送状态机和 DMA         |

正常的高频遥测链路可以简化成：

```text
wifi_justfloat()
    -> 添加时间戳并打包 JustFloat
    -> 放入 256 帧软件队列
    -> wifi_justfloat_Poll()
    -> wifi_cmd_SendBuffer()
    -> wifi_spi_send_buffer()
    -> wifi_spi_send_poll() 分步推进
    -> DMA 发送数据载荷
    -> 触发 UDP 发包
    -> VOFA+ / 自己写的上位机
```

这个调用链里，`wifi_justfloat()` 更接近“把这一帧数据交给发送系统”，不代表函数返回时数据已经到电脑了。真正的 SPI 发送、模块应答和 UDP 刷新，是后面的 `wifi_cmd_Poll()` 一点一点推进的。

## 为什么选择 UDP

我这里发送普通日志使用的是 UDP，而不是 TCP。TCP 和 UDP 的详细区别网上资料很多，我就不照着教科书重新抄一遍了，只讲它为什么适合这架飞机。

我的需求是不断发送最新的状态，而不是保证每一帧日志都必须到达。比如第 351 帧姿态数据丢了，第 352 帧马上又会来；这时候让飞控停下来重传第 351 帧，对控制没有任何帮助，反而可能破坏实时性。UDP 没有面向电脑端的连接和重传流程，模块只管把数据报发到配置好的 IP 和端口，不需要等 VOFA+ 回一句“我收到了”。

这就带来一个很好用的特性：

- 电脑没开，不影响飞机运行。
- VOFA+ 没打开，或者上位机崩了，不影响飞机运行。
- 上位机偶尔丢包，只损失几帧调试数据，不会反过来卡住飞控。

不过这里要区分两层通信。电脑和 WiFi 模块之间走 UDP，没有接收端确认；MCU 和 WiFi 模块之间仍然是 SPI 私有协议，依然需要看模块的就绪引脚和回复。因此“用了 UDP”不等于从 MCU 到电脑的整条链路都完全没有握手，也不等于底层驱动天然不会阻塞。后面的状态机和调度改造就是为了解决这一层问题。

## 相比逐飞原生驱动，我具体改了什么

逐飞原来的 `wifi_spi_send_buffer()` 是一个比较典型的同步发送函数。它拿到互斥锁之后，会在 `while (length)` 里面等待模块空闲、发送一段数据、读取模块回复，再继续下一段；数据全部发完后，还要继续把剩余回复读干净，最后才释放互斥锁并返回。

这种写法放在普通 Demo 里很直接，也很容易理解。但是放到 `1 kHz` 飞控里问题很明显：调用者不知道这一帧会等多久。模块稍微慢一点、回复晚一点，控制任务就可能跟着等。平均耗时不大也没有用，飞控更怕的是偶尔突然冒出来的长耗时和抖动。

现在的实现主要做了下面这些改动：

| 对比项       | 逐飞原生发送方式                        | 当前工程的发送方式                               |
| ------------ | --------------------------------------- | ------------------------------------------------ |
| 函数行为     | 在一次调用里等待并完成整段发送          | 先复制并提交一帧，马上把执行权还给主循环         |
| 发送过程     | `while (length)` 一直处理到结束或超时 | `wifi_spi_send_poll()` 每次只推进一个状态      |
| 大段载荷     | CPU 通过普通 SPI 搬运                   | 优先使用 PDMA 搬运，DMA 启动失败才退回普通 SPI   |
| 模块等待     | 调用发送函数时同步等待                  | 拆到后续轮询，不把整笔事务塞进一次调用           |
| 忙状态       | 主要靠函数内部互斥                      | 对外提供`wifi_spi_is_busy()`，上层先判断再提交 |
| 多帧高频数据 | 上一帧没发完时容易直接顶住调用者        | 前面增加 256 帧软件队列，生产和发送解耦          |
| 拥塞时的选择 | 调用者可能被通信时间拖住                | 队列满了就丢遥测，优先保证飞控继续运行           |

底层发送状态大致是：

```text
WAIT_SEND
    -> SEND
    -> DMA_WAIT
    -> TX_WAIT
    -> DRAIN_REPLY
    -> DONE
```

它把“等模块可以发送”“发包头”“DMA 搬数据”“等 SPI 真正发送完成”“读掉模块回复”“释放忙状态”拆开了。主循环每调用一次 `wifi_spi_send_poll()`，只把当前事务往前推一步，然后就返回。这样一笔 WiFi 通信不再是一整块不可分割的长任务，1 kHz 控制任务有机会在这些步骤之间先运行。

DMA 的意义也不只是让平均速度更快。更重要的是发送较长载荷时，不需要 CPU 自己一个字节一个字节地守着 SPI 搬数据，主循环的抖动会小很多。代码里还保留了普通 SPI 回退：如果 DMA 没有成功启动，这一帧仍然能走普通发送，不至于因为 DMA 配置异常直接完全失去遥测。

但我也不想把它吹成“全链路完全异步”。目前包头发送、模块就绪检查、回复清理、UDP 立即发送、初始化和文本回包仍然会消耗 CPU，有些地方也会短时间等待。尤其 [`wifi_cmd_SendLine()`](../../project/code/Protocols/wifi/wifi_cmd/wifi_cmd.c) 为了避免文本回包和二进制遥测互相撞包，会主动串行等待，它适合参数查询和标定提示，不适合拿来做高频日志。高频数据要走 `wifi_justfloat()` 这条链路。

## 256 帧队列解决了什么

只有底层状态机还不够。控制环可能每 `1 ms` 产生一帧数据，但是 WiFi 模块不一定刚好在这一刻空闲。如果没有上层队列，发送忙时这一帧只能立刻失败，或者让控制环在原地等。现在 [`wifi_justfloat.c`](../../project/code/Protocols/wifi/wifi_justfloat/wifi_justfloat.c) 里维护了一个 `256` 帧的环形队列：

1. 控制代码调用 `wifi_justfloat()`，把这一时刻的数据快速打包并入队。
2. `wifi_cmd_Poll()` 在主循环空闲时间检查底层是否空闲。
3. 空闲时取出队头一帧，交给 SPI 状态机。
4. 底层发送完，再继续取下一帧。

当前代码还限制了每个 `1 ms` tick 最多入队一帧。也就是说，同一个毫秒里就算有好几个地方都调用 `wifi_justfloat()`，也不会真的生成好几帧去瞬间挤爆链路。每帧会自动在第一个通道放入 `tick_1000us_cnt` 时间戳，后面才是我传进去的用户变量，分析日志时可以直接根据这个通道检查周期和丢帧。

队列的意义是吸收短时间抖动，不是凭空增加带宽。按最大 `408 Byte/帧` 计算，队列本体大约占 `256 x 408 = 104448 Byte`，还不包括长度数组和临时发送缓冲。若以 `1 kHz` 产生数据，它最多只能吸收大约 `256 ms` 的积压。如果生产速度长期大于发送速度，队列最终还是会满。

队列满时当前实现会放弃新遥测，而不是停下来等位置。这正是我想要的取舍：日志可能缺一段，但是姿态和控制周期不能因为日志堵塞。目前代码还没有导出队列深度和累计丢帧数，所以“调用成功”不能被理解成“每帧一定到达上位机”。如果要做严格的数据完整性实验，应该同时检查时间戳是否连续，而不是只看 VOFA+ 有没有曲线。

## 为什么 WiFi 插没插都不影响飞行

这部分最好按具体情况说清楚，不然一句“不影响”很容易让人误解。

| 实际情况                       | 当前行为                                                            | 对飞行的影响                                                              |
| ------------------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 上电前就没有插 WiFi 模块       | 初始化阶段会复位并探测模块，失败后`s_wifi_cmd_ready` 保持为 `0` | 会增加一次上电探测等待；进入运行态后，WiFi 轮询直接返回，不再参与飞行循环 |
| 模块插着，但热点名称或密码不对 | 连接阶段会等待，连接超时配置约为`10 s`                            | 启动会变慢；初始化失败后继续以无遥测状态运行                              |
| 模块和热点正常，但电脑没开     | UDP 仍然只向目标 IP 和端口发送，不等电脑确认                        | 不会因为电脑缺席卡住飞控                                                  |
| 电脑开着，但 VOFA+ 没开        | 没有应用层接收者，UDP 数据直接丢掉                                  | 不影响飞控，只是看不到日志                                                |
| 飞行中网络偶尔丢包             | 对应遥测帧丢失，后续帧继续发送                                      | 控制不等待重传                                                            |

代码上的原因也很直接：`wifi_cmd_Init()` 只有在模块初始化和 Socket 建立都成功后，才把 `s_wifi_cmd_ready` 置为 `1`。如果启动失败，运行时的 `wifi_cmd_Poll()` 一进来就返回；`wifi_justfloat()` 检查到链路没有就绪，也不会进入 SPI 发送路径。所以没有插模块时，不会在飞机已经进入正常运行以后，每个控制周期都傻等一次超时。

需要注意的是，**不插模块不会影响进入运行态后的飞行，不代表上电完全没有等待**。底层普通操作的超时常量约为 `1000 ms`，连接热点的超时常量约为 `10000 ms`，因此缺模块或缺热点时，启动阶段会明显慢一点。这个代价发生在起飞以前，我认为可以接受，也比把等待带进飞行循环安全得多。

另外，我没有把“飞行中热拔 WiFi 模块”当成已验证功能。模块本来已经初始化成功后突然被拔掉，属于另一条故障路径，底层状态机仍可能碰到模块就绪等待。正常使用就是上电前决定插不插，不建议拿热拔插去验证飞机到底会不会掉下来。

所以更准确的结论是：**不插模块会增加一次上电探测等待，但进入运行态后不会拖住飞控；不开电脑或不开 VOFA+，也不会让 UDP 等待接收端。**

## 飞控任务为什么不会被 WiFi 抢在前面

非阻塞驱动还要配合正确的调度位置才有意义。在 [`main_cm7_0.c`](../../project/user/main_cm7_0.c) 的 Core0 主循环里，会先把积压的 `g_tick_1000HZ` 快速任务处理完，再调用 `wifi_cmd_Poll()`：

```text
先处理所有待执行的 1 kHz 快速任务
    -> 再推进一次 WiFi 状态机
    -> 没有快速任务积压时，再执行低频时间片
```

也就是说，只要 1 kHz 控制任务已经到点，优先级永远在 WiFi 前面。WiFi 使用的是两次实时任务之间剩下来的主循环时间，而不是反过来让飞控见缝插针。

飞行状态下，`wifi_cmd_Poll()` 还会在推进发送、处理 UDP 刷新和 JustFloat 队列之后直接返回，不再读取和解析文本命令。参数修改、Flash 操作、IMU 校准这些不确定耗时的事情都留在待机、未解锁状态处理。这样可以避免飞行过程中有人误发一条命令，突然把复杂的字符串解析或参数操作塞进控制循环。

## 一帧到底有多大，能发多少数据

当前 JustFloat 最多支持 `100` 个用户浮点变量，不是旧说明里的 `16` 个。程序还会自动在最前面增加 `1` 个时间戳浮点数，最后再加 `4 Byte` 的 JustFloat 帧尾。因此传入 `N` 个用户变量时：

```text
每帧字节数 = 4 x (N 个用户变量 + 1 个时间戳) + 4 Byte 帧尾
           = 4N + 8 Byte
```

只算 JustFloat 原始有效载荷，不算 UDP/IP、WiFi 和 SPI 的额外包头，常见数据量如下：

| 用户变量数 | 单帧大小 |    100 Hz |                     1 kHz |
| ---------: | -------: | --------: | ------------------------: |
|         10 |  48 Byte |  4.8 kB/s |                   48 kB/s |
|         39 | 164 Byte | 16.4 kB/s |                  164 kB/s |
|         60 | 248 Byte | 24.8 kB/s |                  248 kB/s |
|        100 | 408 Byte | 40.8 kB/s | 408 kB/s，约 3.264 Mbit/s |

这里的 `408 kB/s` 是“每毫秒生产一帧、每帧 100 个用户变量”算出来的理论原始载荷，不是我保证的稳定无线吞吐量。真正在线路上发送时还要加协议开销，实际能不能长期跟上，也会受到 SPI 时钟、WiFi 模块缓存、路由器、信号质量以及 `wifi_cmd_Poll()` 获得多少空闲时间的影响。

实际调试时，不是变量越多、频率越高就越高级。IMU 六轴频谱确实值得以 `1 kHz` 发，因为高频振动信息降采样后可能直接没了；普通姿态、位置和 PID 曲线很多时候 `50-200 Hz` 就已经够用。先问清楚自己想观察什么，再决定采样率和通道数，链路会稳定很多。

## 实测 CPU 占用

历史提交 `4b6a2cd` 专门测过常用函数的执行时间，当时记录的数据是：

- 单独调用 `wifi_justfloat()`：`99 / 10000 = 0.0099 ms`，约 `9.9 us/次`。
- 调用 `wifi_justfloat() + wifi_cmd_Poll()`：`433 / 5000 = 0.0866 ms`，约 `86.6 us/次`。
- 按两者差值粗略估算，当时 `wifi_cmd_Poll()` 额外花费约 `76.7 us/次`。

当前源码注释里仍然保留了 `wifi_justfloat()` 约 `10 us`、`wifi_cmd_Poll()` 约 `88 us` 的记录。按组合测量的 `86.6 us/次` 线性估算，如果固定频率调用，CPU 时间大致是：

| 调用频率 | 每秒占用 CPU 时间 | 换算为单核占比 |
| -------: | ----------------: | -------------: |
|    50 Hz |         4.33 ms/s |      约 0.433% |
|   100 Hz |         8.66 ms/s |      约 0.866% |
|   200 Hz |        17.32 ms/s |      约 1.732% |
|    1 kHz |         86.6 ms/s |       约 8.66% |

这张表只能说明那次测试的大致量级，不能当成现在任何场景下都恒定不变的整机 CPU 占用。状态机这一次走到 DMA 等待，和这一次需要发包头、清回复，耗时肯定不同；数据长度、编译优化、模块状态和主循环调用方式也都会影响结果。尤其 `wifi_cmd_Poll()` 在当前工程里是放在空闲主循环持续调用的，并不是严格按表里的某个固定频率执行，所以表格更适合拿来做预算，不适合拿来冒充实时 CPU 监控结果。

还有一个很容易搞混的地方：`wifi_justfloat()` 的约 `10 us` 只包括打包、复制和提交，不包括数据真正到达上位机的全部成本。完整通信的主要工作在后续 `wifi_cmd_Poll()` 和 DMA 中完成。

## 平常怎么发送日志

普通浮点遥测只需要调用 `wifi_justfloat()`。例如调姿态和高度控制时，可以写成：

```c
wifi_justfloat(g_euler.roll,       /* I1 */
               g_euler.pitch,      /* I2 */
               g_euler.yaw,        /* I3 */
               height_fused,       /* I4 */
               height_target,      /* I5 */
               height_pid.output); /* I6 */
```

上位机可以用 [VOFA+](https://www.vofa.plus/)，协议选择 JustFloat；也可以自己写 UDP 接收程序，只要按相同顺序解析 `float` 和帧尾即可。需要记住，程序自动添加的时间戳是第一个通道，所以注释里的 `I1` 对应上位机看到的第二个浮点通道。发送端变量顺序和上位机通道顺序必须保持一致。

我以前会在很多算法旁边散落一些临时的 `wifi_justfloat()`，发布版本里可能已经删掉或者注释掉了。要看现成例子，可以直接在工程里搜索 `wifi_justfloat(`。不过同一个 `1 ms` 内只有第一次成功入队，所以不要指望在同一周期的三个不同位置各调用一次，就得到三组独立数据。真要同时观察这些变量，放进同一次调用最清楚。

使用时我建议遵守下面几个规则：

- 高频二进制数据统一走 `wifi_justfloat()`，不要用文本 `printf` 或 `wifi_cmd_SendLine()` 代替。
- `wifi_cmd_Poll()` 放主循环空闲区持续运行，不要塞进姿态或控制闭环内部。
- 只有确实需要看高频细节的数据才发 `1 kHz`，其他日志主动降到 `50-200 Hz`。
- 上位机发现数据断层时先看自动时间戳，区分是算法没执行，还是遥测队列或网络丢帧。
- 调试结束后把无关通道关掉，少发一个无用变量就少一点复制、内存和带宽开销。

## 它不只是一个“无线串口”

这套 WiFi 协议后来已经不只是发曲线了，常用功能主要还有下面几类。

### 在线参数

[`wifi_params`](../../project/code/Protocols/wifi/wifi_params/) 支持 `get`、`set`、`list`、`save`、`load` 等命令。能修改的变量必须先进入白名单，`set` 只修改 RAM，确认合适后再用 `save` 写入 Flash。这样调 PID 时不用每改一个数就重新编译下载，但也不会因为上位机随便发一个名字，就改到不该改的内存。

参数读取、修改和 Flash 操作限制在待机且未解锁状态，飞行中不会处理。`start` 和 `stop` 只控制待机时的 JustFloat 遥测，不会关闭文本命令本身。

### IMU 校准

[`wifi_cal_imu`](../../project/code/Protocols/wifi/wifi_cal_imu/) 支持陀螺仪静态校准、加速度自动或手动椭球标定、查看标定进度、检查结果以及保存到 Flash。加速度椭球标定需要采很多不同姿态点，如果没有这条无线命令和状态回传链路，拿着飞机反复插线、看串口会很麻烦。

校准这种可能持续很久、还会写 Flash 的操作同样只允许在待机未解锁状态执行。具体命令和回包格式可以直接看 [`WiFi 协议总览`](../../project/code/Protocols/wifi/README.MD)，这里不重复抄一遍。

### 图像模式

把 [`WIFI_IMAGE_ENABLE`](../../project/code/Protocols/wifi/wifi_cmd/wifi_cmd.h) 设为 `1` 后，通信会切到 TCP 图像模式，并停用普通 JustFloat 链路。图像需要完整帧，需求和高频状态遥测不同，所以没有硬塞在同一个 UDP JustFloat 通道里。正常飞控调参和日志回传保持 `0` 即可。

### 文本命令

所有文本命令必须以 `\r\n` 结束，成功和失败分别统一返回 `OK ...` 与 `ERR ...`。提交文本回包时会和正在发送的 JustFloat 串行，避免二进制数据与文字交叉在一起导致两边都无法解析。这个设计优先保证协议正确，但是也再次说明：文本通道适合低频命令，不适合持续刷日志。

## 常见误区和边界

- **非阻塞不等于零开销。** 数据仍然要打包、复制、通过 SPI 搬运，模块回复也仍然要处理，只是这些工作被拆开并放到了合适的位置。
- **有 256 帧队列不等于永远不丢。** 队列只能吸收短时抖动，平均生产带宽超过发送带宽后一定会满。
- **UDP 不保证每帧到达。** 它正是用可靠性换低等待和简单性，因此严谨分析日志时要检查时间戳。
- **不开电脑和飞行中热拔模块不是一回事。** 前者不会让 UDP 等接收端；后者没有作为正常功能验证，不建议尝试。
- **初始化失败后不拖飞控，不代表上电不等待。** 没有模块或热点时，启动阶段仍然要经历探测或连接超时。
- **文本发送不是高频接口。** 参数、状态提示和校准回包可以用文本，连续波形必须走 JustFloat。
- **图像模式和普通遥测模式不是同时工作的。** 开启图像模式后会关闭 JustFloat，并切换传输方式。

## 这套驱动是怎么一步步改出来的

这部分不是一次就设计好的，Git 历史里能看到比较完整的演变过程：

## 我对这部分的理解

以前我可能会更关注一个算法最后有没有把飞机调稳，现在我越来越觉得，调试链路本身也是飞控的一部分。你必须知道每个通信函数大概花多少时间、算法有没有堵住更高优先级任务、传感器原始数据到底长什么样。没有这些东西，很多所谓“调参”其实只是在猜。

当然，这套实现也不是绝对完美。它会丢包，没有队列占用率统计，启动失败仍然有等待，飞行中热拔模块也没有专门做完整的故障恢复。但它已经满足了我最在意的事情：平常加几个变量就能直接看高频曲线；电脑和上位机不在线时飞机照样运行；WiFi 的主要发送工作被拆到空闲时间，出了问题也不会让遥测的重要性高过飞行本身。

对于这种辅助模块，我觉得“失效以后主系统还能继续干正事”，比功能看起来多高级重要得多。
