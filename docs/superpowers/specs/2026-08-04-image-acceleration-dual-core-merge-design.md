# 图像加速与双核通信合并设计

## 目标

在飞机子仓库当前 `35_small` 分支上合入 `origin/image_Acceleration`，保留现有未提交的 WiFi SPI、IPC、共享内存和飞控修改，同时排除队友对电机驱动频率的修改。合并结果需要维持电机 PWM 400 Hz，恢复主要图像目标的多帧确认，并保持 Core0、Core1、图像板之间的非阻塞通信。

## 已确认基线

- 当前分支与 `origin/35_small` 均指向 `58aa342f926ff647e474d28a1a38c9ea7bb1442f`。
- `origin/image_Acceleration` 指向 `99b39c5ba04231e8f20d2f65c642a83d5fdbc34a`，可以从当前分支快进合入。
- 当前工作区有 8 个未提交文件，全部视为用户已有修改，不得丢失或覆盖。
- 队友分支未修改 `camera_spi.c/.h`、IPC 驱动和共享内存协议结构。
- 队友的 `Motor_Drive.c/.h` 把 PWM 从 400 Hz 改成 200 Hz，本次明确不合入。

## 合并策略

1. 使用 stash 完整保护当前 8 个未提交文件。
2. 使用 fast-forward 合入 `origin/image_Acceleration`，保留队友提交历史。
3. 将 `Motor_Drive.c/.h` 恢复为合并前 `35_small` 版本，继续保持 400 Hz。
4. 恢复 stash，并只解决实际重叠文件的冲突。
5. 对 `main_cm7_1.c` 手工合并，其他文件不做无关整理。
6. 修复图像主要目标的确认状态机，再进行协议和工程检查。
7. 最终业务变更使用中文提交信息提交。

## Core1 主循环设计

`main_cm7_1.c` 同时保留两边的必要行为：

- 保留队友的 `image_down_horizon_init()`。
- 在相机新帧就绪时，先轮询并更新该帧对应的姿态与地平线，再调用 `image_down_update()`，避免地平线数据滞后一帧。
- 姿态不可用或超时时继续执行已有失效处理，不能让旧地平线无限生效。
- 保留本地饱和 tick 语义：中断只把 `g_image_tick_100hz` 置 1，主循环消费后清零，避免计数积压造成突发执行。
- 保留本地非阻塞 `CameraSpi_Service()` 调度结构，不新增等待图像板响应的阻塞循环。
- 保留本地 `ipc_image_poll()` 和 IPC 回调只置 hint 的结构，避免在中断回调内处理共享数据。

## 图像目标确认设计

队友加速版本中，B0 信标和强车灯首帧会直接进入 confirmed，单帧误检随后可能由预测逻辑持续输出。合并时恢复主要目标的 pending/confirmed 多帧确认语义：

- 新目标先进入 pending。
- 只有连续匹配达到 `g_image_down_confirm_frames` 后才进入 confirmed 并允许对外输出或丢失预测。
- pending 目标一旦遇到连续空白帧，不得转成预测目标。
- confirmed 目标继续使用现有丢帧容忍和预测策略，不扩大本次修改范围。
- B0 与强车灯不再通过首帧特殊路径绕过统一确认阈值。

最低验证场景为“单帧有效目标，随后连续空白帧”：在没有达到确认帧数时，所有后续帧均不得出现约 240 ms 的幽灵目标输出。

## IPC、共享内存与 SPI 边界

- 保留 `ipc_try_send_data()`、静态异步发送缓冲区和飞行状态非阻塞发送。
- 保留当前 IPC 中断优先级和 Core0 重试行为，不引入新的忙等。
- 保留 IPC 姿态结构的 64 字节对齐及 cache clean/invalidate 防护。
- 核对 Core0、Core1 对共享结构的字段顺序、尺寸和固定地址完全一致。
- 保留 Core0 当前 WiFi SPI 的发送字段及图像诊断内容。
- CameraSpi 继续使用 Core1 SCB6 主机、现有帧格式和协议常量，不修改 `camera_spi.c/.h`。
- 通过协议定义和图像板提交 `fcb0e1befe4addf384e84af5142ff75f5a0fc099` 做静态兼容性核对，重点检查帧头、长度、字节序、校验、解锁状态和响应字段。

## 验证标准

- `git diff --check` 通过，最终差异不包含无关格式化。
- `Motor_Drive.c/.h` 与合并前 `35_small` 内容一致，PWM 配置仍为 400 Hz。
- 单帧主要目标后接连续空白帧时，不产生预测续航目标。
- `ipc_remote_param_mailbox_t`、`ipc_attitude_data_t` 等跨核结构尺寸和两核声明一致。
- IPC 共享段地址无重叠，Core0/Core1 链接配置一致。
- CameraSpi 协议与图像板目标提交一致，服务流程中没有新增阻塞等待。
- CM7_0、CM7_1 工程源文件和单文件优化配置完整。遵守仓库约束，不从命令行调用 IAR；实际构建通过可用的 IAR 图形环境完成，若当前环境无法操作则明确列出待用户执行的两个构建项。

## 台架验证边界

以下项目必须在硬件上完成，代码和静态检查不能替代：

- 观察 CameraSpi 的 `rx_ok_count`、`rx_error_count` 和 `online`。
- 测量 Core0 到 Core1/图像板的解锁状态传播延迟。
- 用示波器确认电机 PWM 周期仍为 2.5 ms，即 400 Hz。
- 实际注入单帧目标和连续空白帧，确认无幽灵目标输出。

## 非目标

- 不重构现有飞控、IPC 或图像算法模块。
- 不修改 CameraSpi 对外协议。
- 不修改图像板仓库提交。
- 不删除或整理与本次合并无关的旧代码。
